# OWCA v0.7.1 loadout UI refinement design

- Status: approved direction for implementation planning
- Target: `0.7.1-dev` on draft PR #13
- Date: 2026-08-15

## Goal

Make the Loadout stage in Create Character understandable to a player while preserving the detailed standalone Manage Loadout editor for maintenance, migrations, corrections, and troubleshooting. PR #13 remains a draft and must not merge until the player-facing workflow is implemented, tested, and inspected.

## Chosen approach

Use one inventory domain and service with two presentation modes:

- **Creation mode** presents only the decisions a player needs before completing a new character.
- **Maintenance mode** retains custody, provenance, reconciliation, audit history, quantities, notes, and corrective operations.

The shared domain remains authoritative. Creation mode hides technical concepts; it does not bypass validation, rewrite catalogue definitions, or create a second inventory model.

Two alternatives were rejected:

- A separate creation-only inventory implementation would duplicate mutation and validation logic.
- Merely collapsing the current technical sections would leave technical terminology and an unclear task order in the primary player workflow.

## Creation-mode structure

The stage contains three primary sections in this order:

1. **Starting Equipment**
   - Prepare calculated grants through one player-facing action when needed.
   - Display prepared equipment grouped as Weapons, Armour, Ammunition, and Gear.
   - Mark starting equipment clearly and protect it from ordinary removal in creation mode.
2. **Add Optional Equipment**
   - Provide text search, a category filter, readable item or weapon details, and one prominent Add action.
   - Default additions to character custody, carried location, Common craftsmanship, and an appropriate later-acquisition origin.
   - Let the player remove optional additions without exposing custody or provenance controls.
3. **Review and Finalize**
   - Show compact carried-weight and armour-by-location summaries.
   - Provide one primary **Finalize Loadout and Continue to Review** action.
   - Explain the exact blocking condition beside the action in player-facing language.

The creation mode does not display custody selectors, origin selectors, reconciliation enums, audit history, durable instance IDs, raw lifecycle values, or Comrade administration.

## Starting-grant behavior

Entering or preparing the Loadout stage materializes calculated starting grants idempotently. Intact grants remain reconciled automatically. If earlier character choices change, creation mode reports that starting equipment no longer matches and offers a **Restore Starting Equipment** action.

Detailed exchange, loss, transfer, and correction handling remains in Manage Loadout. Creation mode does not ask a player to understand reconciliation terminology merely to accept their calculated starting package.

## Equipment information

Every visible item uses the catalogue name and concise profile already calculated from immutable definitions. Weapon entries show the relevant Damage, Penetration, Range, Rate of Fire, magazine, Reload, and qualities without exposing save-record internals. Armour shows coverage and AP. Other equipment shows quantity, category, weight when the source provides it, and a concise summary or source reference where useful.

## Weight rule

A valid catalogue definition without a printed weight contributes `0 kg`. Its absence does not make the carried total partial and does not prevent a `within_limit` result. This follows the supported source data until a verified weight becomes available.

A missing catalogue definition is different: OWCA cannot resolve the item at all, so the record remains visible as unresolved and finalization remains blocked. The implementation and tests must keep these two cases distinct.

## Maintenance mode

The standalone Manage Loadout workflow retains the full editor introduced in v0.7.0. It remains the place for:

- character, Comrade, and squad custody;
- equipped, carried, and stored locations;
- craftsmanship, origin, quantities, splitting, notes, and removal;
- starting-grant exchange, loss, transfer, and correction records;
- audit-history inspection; and
- recovery of unusual or migrated records.

This technical density is acceptable in the explicit maintenance and troubleshooting surface, but not in Create Character.

## Errors and messages

Creation messages describe the corrective action rather than the internal state. Examples:

- “Prepare your calculated starting equipment before continuing.”
- “Starting equipment changed after an earlier character choice. Restore it before finalizing.”
- “One owned item is no longer available in the equipment catalogue. Open Manage Loadout after saving to resolve it.”

The UI must not present raw enum values such as `unprepared`, `draft`, `present`, or `correction` as instructions to a player.

## Compatibility and boundaries

The v4 character state, inventory events, durable identities, ownership model, and interoperability schema `1.3.0` remain unchanged. The weight-calculation output changes for valid definitions without a printed weight, so calculated previews and tests must be updated. Weapon modifications, requisition, combat ammunition expenditure, campaign advancement, and new save fields remain outside v0.7.1.

## Verification

Automated coverage must confirm:

- creation mode exposes the three primary sections and one finalization action;
- creation mode hides custody, provenance, reconciliation, audit, and identity controls;
- optional equipment uses the declared defaults and can be removed safely;
- intact starting grants prepare and reconcile without technical player input;
- changed grants offer a restore action and still prevent premature finalization;
- valid definitions without printed weight contribute `0 kg` and allow a complete encumbrance result;
- missing definitions remain unresolved and block finalization;
- maintenance mode retains every detailed v0.7.0 control;
- both modes remain horizontally usable at 960x650; and
- save/load, migration, dossier, and inventory-domain tests continue to pass.

A manual Godot inspection must verify task order, wording, scroll length, primary-action visibility, readable item profiles, and the transition from Loadout to Review at the minimum and standard window sizes.

## Release gate

PR #13 stays draft until the v0.7.1 implementation, automated suite, manual creation-flow inspection, and printable dossier check pass. Further player feedback may produce additional `0.7.x` refinements before v0.8.0 begins.
